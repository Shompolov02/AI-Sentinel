# Контекст проекта AI-Sentinel

## 1. Статус и назначение документа

Этот файл задает единый предметный язык и архитектурные ограничения проекта. Все требования, код, тесты, API, конфигурации, события и документация должны использовать термины из этого файла. Источник контекста — техническое задание `docs/spec/tz_sazii.pdf`.

Если реализация расходится с этим документом, расхождение должно быть оформлено как отдельное архитектурное решение с обоснованием, оценкой риска и обновлением `CONTEXT.md`. Не определенные в ТЗ детали не следует представлять как утвержденные требования.

## 2. Идентификация и цель системы

- **Полное наименование:** Система активной сетевой защиты и автоматического реагирования на инциденты на базе ИИ-агента.
- **Сокращенное наименование:** САЗИИ — Система Активной Сетевой Защиты с ИИ.
- **Кодовое имя:** AI-Sentinel. В ТЗ также упомянут альтернативный вариант Aegis-Agent; в проекте следует использовать AI-Sentinel.
- **Главная цель:** повысить эффективность обнаружения и нейтрализации сетевых атак посредством автоматизированного триажа автономным ИИ-агентом и исследовать устойчивость агента к Prompt Injection через сетевые интерфейсы.
- **Назначение:** непрерывно наблюдать входящий и внутрисетевой трафик контейнеризированной микросервисной среды, анализировать аномалии и события Honeynet, классифицировать угрозы с помощью LLM, блокировать подтвержденные источники угроз и регистрировать инциденты в DefectDojo.
- **Операционный эффект:** уменьшение MTTR и нагрузки на аналитиков SOC L1/L2 без потери аудируемости решений.

САЗИИ является программно-аппаратным комплексом эшелонированной защиты. Она сочетает Deception Technology/Honeynet, сбор и нормализацию телеметрии, AI-powered triage, SOAR, сетевое принуждение через Netfilter и DevSecOps-контроль поставки.

## 3. Единый предметный язык

| Термин | Каноническое значение |
|---|---|
| Событие безопасности | Нормализованная запись о потенциально значимом действии в инфраструктуре. Передается внутри системы в структурированном JSON-формате. |
| Сырые логи | Исходные журналы хоста, Nginx, stdout контейнеров, целевых приложений и сессий Cowrie до нормализации. |
| Телеметрия | Поток сырых логов, сетевых событий, системных вызовов и служебных метрик. |
| Нормализация | Очистка и преобразование разнородных журналов в единый структурированный JSON-контракт. |
| Honeynet | Изолированный ложный периметр с ловушками; не является боевой средой и не должен иметь неограниченного пути в Production Zone. |
| Cowrie | Высокоинтерактивная SSH/Telnet-ловушка, фиксирующая брутфорс, учетные данные и команды атакующего. |
| Target Web Application / Target App | Преднамеренно уязвимый тестовый веб-сервис для DAST и контролируемых экспериментов. Это не продуктивный бизнес-сервис. |
| AI Agent Core / когнитивное ядро | Асинхронный backend, принимающий нормализованные события, защищающий LLM-вход, выполняющий триаж и формирующий решение. |
| Prompt Guard | Обязательный пред-LLM фильтр регулярных выражений и семантической валидации, обнаруживающий Prompt Injection во входных данных. |
| LLM Client | Адаптер к внешнему LLM API либо локальной Ollama. Не принимает сетевые данные в обход Prompt Guard. |
| Triage Engine | Модуль контекстного анализа, сопоставления с MITRE ATT&CK и назначения критичности `Critical`, `High`, `Medium` или `Low`. |
| Инцидент | Классифицированное событие или совокупность событий с вердиктом, доказательствами, таймлайном и данными о реагировании. |
| Finding | Карточка подтвержденного инцидента, созданная через REST API в DefectDojo. |
| Evidence | Логи, контекст, таймлайн, признаки и результаты анализа, подтверждающие Finding. |
| Firewall Enforcer | Единственный прикладной адаптер, которому делегировано минимально необходимое исполнение операций iptables/nftables. |
| SOAR | Контур автоматического активного реагирования: применение решения, блокировка источника и регистрация инцидента. |
| Подтвержденная атака | Инцидент с критичностью `High` или `Critical`, для которого разрешен сценарий автоматического блокирования по ТЗ. |
| Fail-Safe Network State | Состояние, при котором уже примененные правила Netfilter продолжают действовать при остановке AI Agent Core. |
| Fallback | Эвристический анализ по сигнатурным регулярным выражениям и пороговым счетчикам при недоступности LLM. |
| Security Exception | Явно утвержденное SecOps исключение из политики безопасности с аудиторским следом. |
| MTTR | Mean Time to Respond; время от обнаружения до реагирования, которое система должна сокращать. |
| False Positive | Легитимное событие, ошибочно классифицированное как угроза; один из ключевых объектов измерения и ручной коррекции. |

## 4. Архитектурные принципы и границы

1. **Микросервисы и контейнеризация.** Компоненты развертываются изолированно в Docker; локальная оркестрация задается Docker Compose. Kubernetes/K3s указан как возможная среда распределенного развертывания, но не должен считаться обязательным без отдельного решения.
2. **Эшелонированная защита.** Обнаружение в Honeynet, централизованный анализ, блокировка на хосте и регистрация Finding являются независимыми слоями, а не одним монолитным процессом.
3. **Разделение сред.** Ловушки, Production Zone и управляющие компоненты разделены сетями и контекстами исполнения. Компрометация Honeynet не должна давать путь к боевым компонентам.
4. **Недоверенный ввод.** Любые логи, включая записанные Cowrie команды, являются недоверенными данными. Текст лога никогда не является инструкцией для AI Agent Core или LLM.
5. **Наименьшие привилегии.** Контейнеры работают не от `root`. Исключительные полномочия сетевого адаптера ограничиваются необходимыми операциями Netfilter.
6. **Асинхронность.** Прием событий отделен от ожидания LLM через `asyncio.Queue`; задержка внешней модели не должна блокировать API Gateway.
7. **Безопасная деградация.** Недоступность LLM активирует Circuit Breaker и Fallback, а не останавливает базовое сигнатурное обнаружение и блокировку очевидных атак.
8. **Аудируемость.** Классификация, решение, примененное действие, Finding, ручное исключение и разблокировка должны иметь коррелируемый аудиторский след.
9. **Shift Left.** Небезопасная сборка не развертывается; проверки SAST/SCA и экспериментальная верификация входят в конвейер поставки.

### 4.2. Сетевое разделение

- **Внешняя зона:** недоверенные источники трафика и внешние LLM API. Доступ разрешается только через явно определенные точки входа/выхода.
- **Production Zone / `prod_net`:** целевые микросервисы и их шлюз. Эта сеть изолирована от Honeynet.
- **Honeynet / `honeynet`:** Cowrie и иные decoy-сервисы. Любое обращение к ним считается высокоинформативным событием, но содержимое сессии остается недоверенным.
- **Контур телеметрии:** Fluent Bit читает разрешенные журналы и stdout, буферизует их и передает только нормализованные события на внутренний API Gateway.
- **Управляющий контур:** AI Agent Core, SOAR и интеграции. Прямой доступ ловушек к LLM, DefectDojo или сокету управления хоста запрещен.
- **Контур хоста:** Linux Netfilter и Docker Engine. Firewall Enforcer получает строго ограниченный интерфейс к iptables/nftables; остальные контейнеры не получают эти полномочия.
- **Контур учета:** DefectDojo и PostgreSQL с персистентными томами. Пользовательский и сервисный доступ регулируется RBAC.
- **CI/CD-контур:** GitHub/GitHub Actions, реестр образов и тестовый стенд. Секреты поставляются через GitHub Actions Secrets и переменные среды, не через репозиторий.

Конкретные подсети, порты, политики ingress/egress, TLS/mTLS и метод аутентификации сервисов в ТЗ не заданы. Их необходимо определить до развертывания, сохранив описанные границы доверия и запрет прямого маршрута Honeynet -> Production Zone.

## 5. Состав подсистем

### 5.1. Honeynet Infrastructure

**Назначение:** раннее обнаружение, децепция, изоляция разведки/брутфорса и сбор цифровых отпечатков атакующего.

- Cowrie эмулирует SSH/Telnet и сохраняет сессии и команды.
- Decoys эмулируют уязвимые сервисы.
- Target App предоставляет контролируемые уязвимые endpoint-ы для DAST.
- Nginx/Docker Bridge маршрутизируют входящий трафик и разделяют `prod_net` и `honeynet`.
- Обращение к неавторизованным endpoint-ам и ловушкам фиксируется как событие; легитимный трафик не должен порождать систематические ложные срабатывания.

### 5.2. Telemetry & Log Ingestion

**Назначение:** непрерывный сбор, буферизация, очистка и нормализация телеметрии.

- Fluent Bit работает как агент/демон на хосте и в требуемых контейнерных контекстах.
- Источники: `/var/log/`, Nginx access logs, stdout контейнеров, JSON-логи приложений, сессии Cowrie и системные события.
- Нормализатор формирует единый JSON-контракт.
- Дисковая буферизация (`storage.type filesystem`) предотвращает потерю при всплесках.
- Backpressure приостанавливает вычитку без падения службы и переполнения памяти.

### 5.3. AI Agent Core

**Назначение:** безопасный анализ событий в реальном времени, классификация, решение и формирование материалов инцидента.

- API Gateway принимает нормализованные события только от разрешенного сборщика.
- Prompt Guard проверяет вход до формирования LLM-запроса.
- Событие с признаками Prompt Injection изолируется; попытка отражается отдельной метрикой/событием мониторинга и не передается как инструкция в LLM.
- Triage Engine учитывает IP-адрес, частоту, команды/характер активности и сопоставляет наблюдения с MITRE ATT&CK.
- LLM Client поддерживает внешний API и локальную Ollama, жесткие connect/read timeout 3–5 секунд, обработку сетевых ошибок и Circuit Breaker.
- Результат анализа содержит как минимум уровень критичности, обоснование, техники/тактики MITRE ATT&CK и Evidence.
- При недоступности LLM Fallback продолжает сигнатурный и пороговый анализ.

### 5.4. SOAR & Firewall Enforcer

**Назначение:** применить подтвержденное решение на сетевом уровне и зарегистрировать инцидент.

- Автоматическое активное реагирование допускается для `High` и `Critical`.
- Firewall Enforcer добавляет адрес источника в DROP-правила iptables/nftables. Канонический пример ТЗ: `iptables -I INPUT -s <attacker_ip> -j DROP`.
- Перед исполнением адрес и команда должны проходить строгую структурную валидацию; недоверенная строка не должна конкатенироваться в shell-команду.
- Примененные правила сохраняют действие независимо от процесса AI Agent Core.
- DefectDojo adapter создает Finding с описанием, критичностью, таймлайном, Evidence и результатом реагирования; поддерживает выгрузку отчетов.
- SecOps может вручную снять ложную блокировку, причем действие аудируется.

### 5.5. CI/CD, Research & Verification

**Назначение:** воспроизводимая сборка, контроль качества и безопасности, развертывание стенда и экспериментальная проверка.

- GitHub Actions запускается на изменениях в репозитории.
- Semgrep выполняет SAST исходного кода.
- Trivy выполняет SCA зависимостей и образов по известным CVE.
- В ТЗ SonarQube указан как возможная альтернатива/дополнение SAST, но базовым явно повторяющимся инструментом является Semgrep.
- Критические результаты SAST/SCA останавливают сборку.
- Chaos/Red Team Runner после развертывания тестового стенда генерирует контролируемые атаки, проверяет реакцию и измеряет Latency/Accuracy.
- Отчет проверки связывается с коммитом.
- Ошибка security gate или `chaos-verify` не меняет рабочий стенд; выполняется rollback к предыдущему стабильному состоянию.

## 6. Основные сценарии

### 6.1. Сбор события

1. Fluent Bit наблюдает разрешенные журналы и stdout.
2. Новое событие сериализуется в нормализованный JSON.
3. Событие по внутреннему защищенному каналу поступает в API Gateway.
4. При перегрузке событие остается в дисковом буфере, а backpressure ограничивает чтение.

### 6.2. Безопасный триаж

1. Prompt Guard рассматривает весь текст события как недоверенный ввод.
2. При Prompt Injection событие карантинируется, попытка измеряется и журналируется; LLM не получает вредоносную инструкцию.
3. Допустимое событие обогащается контекстом и анализируется Triage Engine.
4. Наблюдения сопоставляются с MITRE ATT&CK.
5. LLM либо Fallback формирует объяснимый вердикт: `Critical`, `High`, `Medium` или `Low`.

### 6.3. Активное реагирование

1. Для `High`/`Critical` формируется структурированное решение о блокировке.
2. Firewall Enforcer валидирует IP и применяет DROP-правило.
3. Параллельно DefectDojo adapter создает Finding и прикладывает Evidence.
4. Все стадии связываются корреляционным идентификатором и попадают в аудит.

### 6.4. Проверка поставки

1. Коммит запускает GitHub Actions.
2. Semgrep и Trivy проверяют код, зависимости и образы.
3. При прохождении gates тестовый стенд развертывается средствами IaC.
4. Chaos/Red Team Runner выполняет набор атак, включая Prompt Injection.
5. Метрики и отчет публикуются для коммита; неуспех блокирует ввод версии и сохраняет стабильное состояние.

## 8. Научно-исследовательские цели: Prompt Injection и качество AI-триажа

### 8.1. Исследовательский вопрос

Насколько автономный ИИ-агент способен сохранять корректность и предсказуемость классификации и реагирования, когда злоумышленник внедряет управляющие инструкции в сетевые логи, HTTP-поля или команды сессии ловушки?

Prompt Injection здесь является не обычной сетевой сигнатурой, а атакой на когнитивное ядро через недоверенный текст телеметрии. Исследование должно отдельно оценивать безопасность самого агента и качество обнаружения исходной сетевой атаки.

### 8.2. Экспериментальные цели

- сформировать воспроизводимый корпус нормальных событий, сетевых атак и Prompt Injection разной формы;
- проверить, предотвращает ли Prompt Guard изменение системной роли, политики классификации, формата ответа и решения о блокировке;
- сравнить режимы без Guard, с regex-фильтром и с regex + семантической валидацией;
- измерить влияние Guard на False Positive и False Negative для легитимных логов и инъекций;
- оценить точность назначения критичности и сопоставления MITRE ATT&CK;
- измерить end-to-end Latency и MTTR, включая LLM и Fallback;
- проверить устойчивость при недоступности/таймауте LLM, исчерпании квот и всплеске событий;
- убедиться, что инъекция не приводит к выполнению команд, отключению защиты, утечке секретов, обходу аудита или произвольной блокировке;
- обеспечить воспроизводимость результатов в Chaos/Red Team Runner и привязку отчета к версии кода/модели/промпта.

### 8.3. Обязательные классы тестов

- прямые инструкции игнорировать системный prompt или сменить роль;
- инструкции, замаскированные под команду Cowrie, HTTP payload, имя пользователя, User-Agent либо JSON-поле;
- обфускация, разбиение инструкции между событиями, кодирование и многоязычные формулировки;
- попытки заставить модель вернуть управляющую команду или подменить IP для блокировки;
- попытки извлечь системный prompt, API-ключи и конфигурацию;
- ложные похожие фразы в легитимных логах для контроля избыточной фильтрации;
- отказ LLM и переход на Fallback;
- повторная доставка и всплеск одинаковых событий для проверки идемпотентности и backpressure.

### 8.4. Метрики и артефакты

- Accuracy, Precision, Recall и F1 для обнаружения атак и отдельно для Prompt Injection;
- False Positive Rate и False Negative Rate;
- доля успешных инъекций (Attack Success Rate), целевой смысл которой — минимизация;
- корректность MITRE ATT&CK mapping и severity;
- Latency по стадиям и end-to-end, throughput, размер/возраст очереди;
- MTTR от приема события до фактической блокировки;
- доступность LLM, число срабатываний Circuit Breaker и качество Fallback;
- полнота Finding/Evidence и корреляции аудита;
- версия набора атак, кода, модели, системного prompt и конфигурации Prompt Guard.

Численные пороги приемки в ТЗ не заданы. Их следует утвердить до интерпретации эксперимента как успешного.

## 9. Требования информационной безопасности

ТЗ ориентируется на принципы ISO/IEC 27001, NIST Cybersecurity Framework и OWASP API Security Top 10. Упоминание стандартов задает направление контроля, но само по себе не означает сертификацию или полное соответствие.

### 9.1. Доступ и привилегии

- RBAC и Segregation of Duties обязательны для людей и Service Principal.
- Контейнеры запускаются под непривилегированными UID/GID.
- Доступ к Docker socket, host network, Netfilter и иным host-level возможностям запрещен по умолчанию.
- Firewall Enforcer получает минимальный набор операций; AI Agent Core не должен иметь универсальный shell-доступ.
- Сервисные токены AI Agent не используются людьми и не совмещаются с пользовательскими ролями.

### 9.2. Данные и секреты

- API-ключи LLM и учетные данные интеграций не хранятся в коде, образах и логах.
- Секреты поступают через переменные среды и GitHub Actions Secrets; доступ ограничивается назначением сервиса.
- Межкомпонентная передача идет по защищенному внутреннему каналу и через изолированные виртуальные сети.
- Сырые логи и Evidence потенциально содержат секреты/персональные данные; их вывод в LLM требует минимизации и редактирования чувствительных полей.
- DefectDojo/PostgreSQL и дампы Cowrie используют persistent volumes и резервные дампы.

### 9.3. Безопасность решений и команд

- Решение LLM является структурированным предложением, а не исполняемой командой.
- IP-адрес, severity и действие валидируются детерминированным кодом до Enforcer.
- Prompt Guard всегда расположен перед LLM Client и не обходится в fallback/повторной обработке.
- Для внешнего LLM действует явный allowlist передаваемых полей; секреты и лишний контекст исключаются.
- Автоблокировка ограничена `High`/`Critical`; ручная разблокировка и Security Exception доступны SecOps и аудируются.
- Повтор события не должен бесконтрольно дублировать правила или Findings; операции реагирования проектируются идемпотентными.

### 9.4. Аудит и подотчетность

- Код проходит SAST/SCA до деплоя; критический результат блокирует поставку.
- Для каждого инцидента фиксируются входное событие/ссылка на него, результат Guard, способ анализа (`LLM` или `Fallback`), версия модели/правил, MITRE mapping, verdict, Evidence и действие.
- Изменения prompts, Guard, firewall policy, CI/CD и прав доступа являются аудируемыми административными событиями.
- DefectDojo хранит централизованный реестр Findings и отчетов; Auditor имеет read-only доступ.

## 11. Отказоустойчивость и сохранность

- Критические контейнеры (AI Agent, Fluent Bit, Nginx, DefectDojo DB) используют `restart: always` или `unless-stopped` и healthchecks.
- Docker namespaces и cgroups изолируют сбой/перегрузку Honeynet от Production Zone.
- Fluent Bit применяет filesystem buffer и backpressure при DDoS/сканировании и замедлении downstream.
- LLM Client использует connect/read timeout не более 3–5 секунд, Circuit Breaker и Fallback.
- `asyncio.Queue` не позволяет ожиданию LLM блокировать входной шлюз; очередь должна иметь наблюдаемые пределы и политику перегрузки.
- Примененные правила Netfilter продолжают действовать при перезапуске AI Agent. Необходимо отдельно определить восстановление правил после перезагрузки хоста, поскольку ТЗ гарантирует сохранение при остановке процесса, а не обязательно при reboot.
- PostgreSQL DefectDojo и сессии Cowrie находятся в named volumes; выполняются регулярные дампы БД.
- CI/CD атомарен: неуспешная проверка или deploy/chaos-verify сохраняет предыдущую стабильную версию.

## 12. Нефункциональные инварианты и критерии готовности

Функция не считается завершенной, если нарушено хотя бы одно условие:

- недоверенный лог может миновать Prompt Guard перед LLM;
- решение LLM может напрямую исполниться как shell-команда;
- Honeynet получает неограниченный маршрут в Production Zone или управляющий контур;
- секрет попадает в Git, образ, обычный лог, Finding или запрос внешней LLM без необходимости;
- событие невозможно проследить от приема до verdict, firewall action и Finding;
- отказ LLM полностью останавливает обнаружение очевидных атак;
- критический SAST/SCA-результат не блокирует поставку;
- пользователь получает токен Service Principal или совмещает конфликтующие роли без исключения;
- потеря контейнера уничтожает историю DefectDojo или сессии Cowrie;
- тест активного реагирования может воздействовать на адреса вне явно выделенного стенда.

Для изменений бизнес-логики и исправлений обязателен TDD. Минимальный набор автоматизированных проверок должен охватывать JSON-контракт события, Guard, severity policy, MITRE mapping, fallback, таймауты, идемпотентность блокировки, DefectDojo adapter, RBAC и отказные сценарии.

## 14. Открытые решения, которые нельзя домысливать

- точная JSON-схема нормализованного события и контракт verdict/Evidence;
- конкретная LLM, версия модели, системный prompt, лимиты токенов и политика редактирования данных;
- алгоритм семантической части Prompt Guard и численные пороги качества;
- протокол, аутентификация и шифрование внутренних API;
- адресный план, порты, ingress/egress ACL и способ маршрутизации в Honeynet;
- выбор iptables или nftables и механизм безопасного сохранения правил после reboot;
- политика TTL/разблокировки, allowlist и защита от блокировки доверенной инфраструктуры;
- выбор Docker Compose или K3s для целевого развертывания;
- формат корреляционного ID, сроки хранения логов, Findings и исследовательских данных;
- количественные SLO по throughput, latency, MTTR, availability и восстановлению;
- RPO/RTO, расписание резервного копирования и процедура проверки восстановления;
- порядок human-in-the-loop для спорных решений `High`/`Critical`.

До реализации соответствующей области эти пункты должны быть оформлены как явные архитектурные решения и отражены в данном контексте.
