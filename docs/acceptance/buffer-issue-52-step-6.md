# #52: пункт 6 — ограничение приёма и восстановление

Дата: 2026-10-28. База: `e61d17bfdac683ebf138dd7d13564718e186b857`.
Ветка: `codex/issue-52-buffer`. Отчёт относится к незакоммиченным изменениям
пункта 6; полной приёмкой всех AC #52 не является. Параметры и границы TDD
подтверждены владельцем: [контракт](../spec/collector-buffer-v1.md).

## Реализовано

- Раздельные бюджеты payload outbox и chunks по 64 MiB, периоды чтения 2/10 с,
  пороги предупреждения/остановки/возобновления 80/100/60. Перед превышением
  payload-бюджета курсор сохраняется перед непринятой записью, без потери её
  первого receipt. Состояние ограничения сохраняется при перезапуске.
- Контроль фактического свободного места с растущим резервом под SQLite journal
  и подачу Fluent Bit. Нехватка места останавливает чтение с локальным сигналом;
  освобождение места возвращает обычный режим. Это не квота всего Docker-диска.
- Подтверждённый payload outbox освобождается сразу; отдельный deadline сохраняет
  обязанность очистки остаточной копии chunks. Старый подтверждённый payload при
  обновлении освобождается после регистрации receipt источника. Для cursor-only
  legacy сохраняется возможность сначала восстановить receipt из payload.
- Pending-события не копируются повторно в Fluent Bit при каждом цикле.
  Неблокирующий pipe не удерживает блокировку в ожидании свободного места.
  Свежие допустимые записи могут проходить в chunks при ожидании старых;
  перезапуск восстанавливает chunks из долговечного outbox.
- Core сохраняет лимит 1000 и сообщает глубину очереди заголовком. Авторизованный
  HEAD через прежний TLS нужен для обнаружения освобождения очереди при пустом
  outbox. Страница и новые host-порты не добавлены. Loopback health collector
  сообщает режим, безопасные счётчики и состояние дискового резерва.
- Повтор после потери ответа Core возвращает существующую задачу без нового
  аудита/анализа. Отсутствие квитанции collector не доказывает отсутствие задачи.

## Проверки

HTTP tracer bullet сначала упал из-за отсутствия заголовка глубины очереди,
после минимального изменения прошёл. Проверены 800/1000 задач, отказ новой
задаче, авторизация HEAD, восстановление очереди и прежний ID при повторе.
Сценарий потерянного ответа использует настоящий Core HTTP и подменяет только
транспортный сбой после фиксации задачи; API задачи и аудит остаются прежними.

Два новых runtime-сценария запускают настоящий supervisor и Fluent Bit в
контейнере без сети, root, capabilities и Docker socket. Core-транспорт
управляемый, без внешней LLM. Проверяются:

- Outbox 10 000 байт: warning, остановка до превышения бюджета, сохранность
  заполненного буфера, перезапуск в stopped, доставка всех 40 уникальных
  записей после восстановления. ID, received_at и raw_record_ref не меняются.
- Core 800 → 799 остаётся slowed; 1000 → 601 остаётся stopped; 600 возвращает
  normal, в том числе при пустом outbox. Реальное заполнение отдельной tmpfs
  проверяет дисковый резерв; файл в chunks проверяет учёт занимаемого места
  и запаса перед подачей нового пакета.

Существующий runtime #51 проверяет настоящие просроченные и свежие chunks,
их очистку и повтор свежего outbox с управляемым временем. Он выявил задержку
подачи свежих записей при ожидании старых; исправление проверено повторным
успешным запуском без ослабления прежнего теста.

## Оставшиеся границы

Полный Cowrie → TLS → Core и вся приёмка AC2/AC3 остаются пунктами 7–8;
полный quality/security gate и эксплуатационная приёмка — пунктом 9.
Настоящий TLS для нового HEAD пока проверен конфигурацией, а не сквозным
запуском. При обновлении потребуется пересоздать core-intake вместе с Core
и collector. Защита диска не резервирует блоки от сторонних writer.
Чтение collector не останавливает Cowrie: его сырые журналы продолжают расти.

Действующий Compose project пользователя не обновлялся. Три исходных
untracked-файла сохранены побайтно. Коммит, push и PR в этом пункте не создавались.
