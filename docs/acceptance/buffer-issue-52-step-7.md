# #52: пункт 7 — истечение недоставленного буфера

Дата: 2026-10-28. Ветка: `codex/issue-52-buffer`.
База: `e61d17bfdac683ebf138dd7d13564718e186b857`.
Проверяются незакоммиченные изменения после пункта 6, без обновления рабочего
стенда пользователя. Контракт: [collector-buffer-v1.md](../spec/collector-buffer-v1.md).

## Исправления по результатам TDD

1. Тест команды очистки с реальной SQLite и отказом commit сначала выявил
   ложный `buffer_event_expired`: payload оставался в базе после rollback,
   хотя сигнал уже был записан. Теперь удаление payload, намерение очистки
   chunks и безопасное уведомление фиксируются одной транзакцией. CRITICAL
   публикуется после commit. Неотправленное уведомление содержит только event_id
   и переживает перезапуск. Повтор после сбоя подтверждения журнала допустим;
   отсутствие потерь важнее exactly-once локальной диагностической записи.
2. Runtime-тест сохранил открытый дескриптор chunk. Имя файла исчезало после
   graceful shutdown, но дескриптор продолжал читать просроченный текст.
   Смена поколения теперь принудительно завершает только дочерний Fluent Bit,
   дожидается его завершения и затем выполняет усечение/fsync/unlink до снятия
   намерения очистки. Свежий outbox восстанавливается с прежними ID и receipt.
   Истёкший локальный `/deliver` отвечает 503 до очистки и не обращается в Core.
3. Runtime-отказ прав на файл chunks выявил отсутствие отдельного критического
   кода ошибки. Теперь supervisor пишет `retention_cleanup_failed`, завершает
   работу с ошибкой и сохраняет незавершённое намерение для следующего запуска.

## Наблюдаемые сценарии

- CLI → реальные файлы/журнал: отказ мутирующего commit возвращает exit 1,
  сохраняет payload, не сообщает о состоявшемся истечении. Повтор без отказа
  удаляет старый payload, сохраняет свежий и публикует CRITICAL.
- CLI → журнал: отказ logging transport после commit не теряет ожидающее
  уведомление. Новый Journal при повторном запуске публикует его; следующий
  обычный запуск уже не повторяет сигнал. Внутренние таблицы в assertions
  не читаются и не подменяются; подменены внешние SQLite/logging ошибки.
- Реальные supervisor + Fluent Bit + HTTP Core работают в отдельном контейнере
  без сети, root, capabilities и Docker socket. Синтетические Cowrie JSON
  читаются обычным нормализатором; Core-транспорт удерживается недоступным.
  Outbox ограничен 10 000 байт, chunks — 4 MiB.
- Команда и попытки входа обоих исходов приняты в день 0, шесть свежих команд —
  начиная с дня 1. Collector достигает stopped; перезапуск не начинает новый TTL.
  На `14d - 1s` старые записи остаются в настоящих chunks, критических сигналов
  об истечении нет. На точной границе `14d` старые маркеры исчезают из всех
  collector-файлов и прежних открытых дескрипторов, свежий маркер сохраняется.
- Журнал получает три CRITICAL с event_id, без task_id и текста. До восстановления
  доставки Core HTTP показывает отсутствие принятых задач и истории сигналов.
  На `14d + 1s` доставка восстанавливается: Core создаёт ровно шесть различных
  задач для свежих записей. Просроченные маркеры не появляются в файлах Core.
  Повторный перезапуск не повторяет штатные уведомления.
- Отказ реальных прав файла chunks не считается успехом: collector останавливается,
  просроченные байты остаются наблюдаемыми до исправления прав. Следующий запуск
  завершает очистку и доставляет только свежие записи.
- Runtime-отказ logging transport после commit также проверен: collector
  завершается с ошибкой, ожидающие уведомления сохраняются. Новый запуск
  публикует три сигнала и очищает прежние inode без доставки просроченного в Core.
