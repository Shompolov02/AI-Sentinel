# #51: пункт 8 — управляемое время и незавершённые задачи

Дата: 2026-10-26. Ветка: `codex/issue-51-retention`, база
`886a90a6ee851609626764aed5b06fd9f1a99685`.
Проверена локальная приёмка сроков 14/30 дней на согласованных границах
нормализатор → HTTP/API/карточка и CLI очистки → реальные файлы.
Полная приёмка Cowrie/Guard, security gate и runbook относятся к пункту 9.

## Что изменено

Проверки выявили и закрыли две гонки на точной границе 14 дней:

- Запрос карточки/API мог получить снимок с текстом до срока, дождаться ответа
  reader после срока и вернуть старый текст. Теперь перед возвратом ответа
  повторно проверяется срок, из снимка удаляются текст, excerpt и raw_url.
  Истечение срока не подменяет подтверждение удаления источника: пока его нет,
  статус остаётся unavailable, raw возвращает 503.
- Ответ Guard мог быть получен до срока, но ожидать блокировку SQLite до его
  наступления. Теперь срок проверяется повторно под блокировкой записи перед
  фиксацией анализа. Просроченный результат не становится новым вердиктом:
  команда завершается failed/text_expired с предупреждением. Результат,
  действительно завершённый до срока, сохраняется после удаления текста.

Проверка миграции также подтвердила политику исторических записей без
`received_at`: общий помощник считает такой текст просроченным. Он не создаёт
новый TTL и не вызывает ошибку карточки после дополнительной проверки ответа;
безопасные метаданные остаются в прежнем 30-дневном сроке.

## Единый сценарий хранения

В новом `test_retention_lifecycle.py` используются реальные нормализатор, Core,
reader, обе SQLite, CLI, файлы JSON, gzip, TTY, служебные журналы, downloads,
карантин и остановленный дисковый буфер. Текст — синтетические уникальные маркеры.
SQL SELECT для проверки внутренних таблиц не применяется: результат наблюдается
через HTTP и чтение байтов всех файлов тестового каталога, включая распаковку gzip.

| Момент по управляемым часам | Наблюдение |
| --- | --- |
| occurred_at = 1 сентября; первый приём = 19 октября; приём Core = 22 октября | Три разных момента; mtime исходника также изменён и не определяет срок |
| Первый приём + 14 суток − 1 секунда | Старый текст и источник ещё доступны |
| Ровно +14 суток | Старый маркер отсутствует во всех проверяемых хранилищах; более свежий остаётся; карантин очищен; reader/raw дают 410; Evidence показывает удалённый источник без фрагмента |
| После удаления текста | Прежние Rules-вердикт High и объяснение команды сохранены; повтор события возвращает прежний ID, не продлевая срок |
| Первый приём + 30 суток − 1 секунда | Задачи и безопасный результат ещё доступны |
| Ровно +30 суток | Задачи дают 404, повтор получает 410; task_id/event_id/raw_record_ref отсутствуют в байтах проверяемых хранилищ; метаданные с приёмом на сутки позже остаются |
| Рестарт после очистки | Удалённые задачи не возвращаются, более свежие доступны |

Дата в этой таблице — тестовое время, а не смена системных часов хоста.
Clock передаётся доверенной конфигурацией тестов; HTTP-управление временем
в продукт не добавлялось. Операционные курсоры и контекст источника сохраняются
по прежней политике и не превращают удалённую историю в новые события.

## Незавершённая работа и ошибки

- Две задачи приняты как queued без запуска worker: команда и вход. После
  очистки сырья и рестарта на точной границе срока последней записи команда
  получает failed/text_expired, без вердикта и текста, с локальным и экранным
  предупреждением. Вход завершается Low/Rules по оставшимся безопасным полям;
  оба Evidence подтверждают удалённый источник.
- Если рестарт происходит уже после обоих 30-дневных сроков, queued-задачи
  удалены до запуска анализа и не оставляют новых ссылок в Core SQLite.
- Настоящая блокировка SQLite удерживается через deadline после ответа процесса
  инференса. Для границы −1 секунда проверено сохранение High и его последующее
  сохранение без текста; для точной границы проверено failed/text_expired.
- Смоделированный ENOSPC на границе SQLite даёт CLI exit 1 и критический
  retention_cleanup_failed, API 503 без текста. Тест подтверждает, что физические
  байты ещё не удалены, и не считает это успехом. После снятия отказа CLI exit 0,
  старый текст отсутствует в файлах Core, свежий сохранён. Недоступный reader
  не объявляется доказательством удаления.

Для управления задержкой инференса подменён только OS-процесс транспорта,
возвращающий фиксированный ответ; Guard adapter, очередь, worker, SQLite и
блокировка реальные. Это доказательство соблюдения срока, а не качества модели.
Семантическая приёмка закреплённых весов Guard остаётся в пункте 9.
