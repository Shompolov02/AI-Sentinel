## Проверенный путь

`test_buffer_stack_runtime.py` создаёт отдельный Compose project с каноническими
Phase 1/Core/collector/evidence/retention overlays, своими named volumes,
случайными loopback-портами и временными credentials/CA. Тестовые часы доступны
через read-only mount; часы хоста и настоящего Cowrie не меняются.
Readiness опрашивается чаще только в тестовом overlay, без изменения самих
health-проб и трёхсекундного timeout loopback-запроса collector.
Стартовый grace period равен 30 секундам, чтобы частый опрос не помечал
ещё запускающийся Python/TLS reader неисправным под нагрузкой.

- Настоящий HEAD проходит collector → CA-verified TLS → Nginx → Core.
  Проверены 200 с глубиной очереди, 401 без сервисного токена, отказ без
  доверенной CA и 404 для внутреннего пути через публичный page ingress.
- Telnet создаёт успешный вход, SSH — неуспешный. Пока intake остановлен,
  реальные команды заполняют outbox с бюджетом 10 000 байт и chunks 4 MiB.
  Наблюдаются warning/critical и stopped, превышение бюджета не допускается.
  Синтетические пароли отсутствуют в доступных collector-файлах; приватный
  heartbeat проверяется своим владельцем как числовая отметка времени.
- Пересоздание collector сохраняет pending-события и received_at. Восстановление
  intake доставляет все команды; каждой buffered-записи соответствует ровно
  одна задача. Rules дают Low неуспешному SSH-входу и High успешному Telnet-входу.
- Во втором цикле три команды приняты в день 0, свежие — начиная с дня 1.
  На `14d - 1s` старые команды остаются в настоящих chunks, сигналов об
  истечении нет. На точной границе `14d` три локальных CRITICAL подтверждают
  истечение; старые маркеры исчезают из collector-data, а набор задач Core
  и история веб-сигналов не получают записей этих недоставленных событий.
- После `14d + 1s` восстановленный intake создаёт ровно восемь свежих задач,
  без задач для просроченных event_id. Cowrie
  сохраняет контейнер и исходную Telnet-сессию; `pwd` проходит тот же путь
  до новой задачи после очистки.
- На том же стенде проверены DNS и прямые IP всех управляющих сервисов и
  Target App в prod_net из Cowrie. Cowrie остаётся только в honeynet;
  collector — только в core_ingest, без host-портов и Docker socket,
  с read-only root/сырьём и cap_drop ALL.

Тест не вызывает внешнюю LLM. Guard не подключается: команды без модели честно
завершаются `guard_unavailable`. Обязательная ML-приёмка из прежнего runbook
этим тестом не заменяется. Внешний сайт Target App и модель угроз не менялись.

## Обнаруженные и исправленные ошибки

1. **Два нормализатора обходили общий бюджет.** Первый сквозной прогон показал
   17 205 байт при лимите 10 000: raw-очиститель тоже вызывал `Journal.scan`
   с прежним default. Теперь он получает тот же бюджет и уступает чтение
   живому collector через lease. При остановленном collector standalone-
   обслуживание ограничено тем же лимитом. Владелец настраивает lease 0660/GID 999.
2. **Сетевое ожидание удерживало глобальный storage gate.** Блокировка
   delivery/reset отделена от SQLite, а health читает счётчики и меняет режим
   одним соединением. Timeout проверки не увеличивался.
3. **Native TTY/service-log очистка монополизировала реестр.** Стеки показали
   ожидание collector на flock, пока raw-очиститель выполнял commit/fsync
   почти для каждого кадра/строки. Очистка теперь работает порциями до 64
   записей, освобождает реестр, сохраняет позицию/размер снимка и не перечитывает
   весь префикс на каждой порции. Порядок durable intent → bytes/fsync → erased
   сохранён; `--once` не сообщает успех до завершения прохода.

Два дополнительных CLI-теста проверяют частичную запись и отказ fsync на
TTY из многих кадров. Повтор восстанавливает очистку, сохраняя заголовки,
размеры и свежую сессию. Старые проверки retention не ослаблялись.

Polling нового harness повторяет предусмотренный контрактом временный HTTP 503
в пределах общего deadline. Итоговый успех требует получить все ожидаемые
задачи/терминальные состояния; 401/404 и другие неожиданные ответы не скрываются.
Отсутствие задач для недоставленного проверяется по полному набору ID страницы,
независимо от доступности подробного raw-source lookup.
Тест восстановления Core не требует обработать все 1000 задач за 10 секунд:
проверяются готовность первой сохранённой задачи, уменьшение глубины и приём
новой задачи после освобождения ёмкости. Неутверждённый throughput SLO удалён.
