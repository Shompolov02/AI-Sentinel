# Фаза 0: инициализация монорепозитория, DevSecOps-каркаса и базовых стандартов качества

## Problem Statement

Проект AI-Sentinel начинает разработку как greenfield-система: сейчас определены предметный контекст, архитектурные границы и требования информационной безопасности, но отсутствуют репозиторий исходного кода, структура подсистем, воспроизводимая среда разработки, автоматические проверки и правила внесения изменений.

Без единого каркаса команды могут по-разному организовать Python-пакеты, зависимости, тесты, контейнеры и CI/CD. Это создаст расхождения между локальной средой и GitHub Actions, усложнит развитие независимых подсистем САЗИИ и позволит небезопасным изменениям попасть в основную ветку без обязательных SAST/SCA-проверок. Для системы, которая в следующих фазах будет обрабатывать недоверенную телеметрию, вызывать LLM и управлять Netfilter, такие расхождения должны быть устранены до появления бизнес-логики.

Фаза 0 должна создать минимальный, но исполняемый фундамент монорепозитория. Результатом является не реализация AI Agent Core, Honeynet или SOAR, а единый способ добавлять, проверять, собирать и сопровождать эти компоненты с соблюдением Principle of Least Privilege, Shift Left и требований аудируемости из `CONTEXT.md`.

## Solution

Создать Git-монорепозиторий AI-Sentinel с логическими областями для сервисов, общих Python-пакетов, инфраструктуры, тестовых/исследовательских средств и проектной документации. Зафиксировать поддерживаемую версию Python, единый менеджер окружения и lock-файл, стандарты форматирования, lint, type checking, тестирования и покрытия.

Добавить одну каноническую верхнеуровневую команду `quality`, которая локально и в CI выполняет одинаковый набор проверок: целостность репозитория и зависимостей, форматирование, lint, статическую типизацию, тесты, SAST, secret scanning, SCA и проверку контейнерной конфигурации. Отдельные проверки остаются доступными для быстрой локальной обратной связи, но обязательный результат определяется агрегированной командой.

Настроить GitHub Actions по принципу least privilege: минимальные permissions, фиксированные версии actions, отсутствие секретов в pull request-проверках, кэширование без подмены lock-файла и fail-closed security gates. Определить правила веток, CODEOWNERS, шаблоны pull request и Security Exception, Renovate/Dependabot-политику обновлений, генерацию SBOM и хранение отчетов проверок.

Каркас должен содержать минимальный smoke-компонент без бизнес-логики, чтобы доказать работоспособность packaging, тестов и контейнерной сборки. Все контейнерные шаблоны запускаются от непривилегированного пользователя, не используют host network, privileged mode, Docker socket или лишние Linux capabilities.

## Implementation Decisions

1. **Границы Фазы 0.** Фаза создает только репозиторный, packaging, testing, container и CI/security каркас. Она не реализует обработку Событий безопасности, Prompt Guard, LLM Client, Triage Engine, Firewall Enforcer, DefectDojo adapter, Fluent Bit, Cowrie или сетевые политики среды исполнения.

2. **Модель монорепозитория.** Репозиторий делится на логические области: развертываемые сервисы, переиспользуемые Python-пакеты, инфраструктура, исследовательские/тестовые инструменты и документация. Каждый развертываемый сервис должен иметь явные зависимости и не импортировать исходный код другого сервиса напрямую. Общий код допускается только через версионируемый workspace-пакет с публичным контрактом.

3. **Python baseline.** Минимальная поддерживаемая версия — Python 3.10 в соответствии с `CONTEXT.md`. CI обязан проверять минимальную версию; основной быстрый job может использовать одну актуальную утвержденную версию. Повышение минимума является архитектурным решением и требует обновления контекста.

4. **Управление окружением.** Выбирается единый Python workspace/package manager с зафиксированным lock-файлом и режимом frozen/sync для CI. Для greenfield-каркаса принимается `uv`: он управляет виртуальным окружением, workspace-зависимостями и воспроизводимой установкой. CI завершается ошибкой, если manifest и lock-файл расходятся.

5. **Метаданные Python.** Конфигурация проекта следует PEP 517/518 и PEP 621. Пакеты используют `src` layout, чтобы тесты не импортировали код случайно из рабочей директории. Runtime- и development-зависимости разделяются.

6. **Стиль и lint.** `Ruff` является единым formatter/linter для Python. Набор правил включает базовые ошибки, импорты, модернизацию синтаксиса в пределах Python 3.10, распространенные bug patterns и security-oriented правила. Любое подавление правила должно быть локальным и содержать краткое обоснование.

7. **Статическая типизация.** `mypy` используется в строгом режиме для нового собственного кода. Ослабления допускаются адресно для внешних библиотек без типов, а не глобальным отключением проверки. Публичные функции и границы пакетов должны иметь явные типы.

8. **Тестовый стек.** `pytest` является test runner, `pytest-cov` формирует покрытие. В Фазе 0 вводится ненулевой gate покрытия для smoke-кода и инфраструктуры тестов; целевой порог для бизнес-модулей устанавливается до их реализации. Coverage не заменяет поведенческие тесты и не должен стимулировать тестирование внутренних деталей.

9. **Единый интерфейс автоматизации.** Верхний уровень предоставляет стабильные команды `bootstrap`, `format`, `lint`, `typecheck`, `test`, `sast`, `sca`, `secrets`, `container-check` и `quality`. Реализация команд может использовать Makefile или совместимый task runner, но CI вызывает те же команды, что и Developer локально. `quality` не изменяет файлы и завершается ненулевым кодом при любой ошибке.

10. **Главный проверочный seam.** Приемка Фазы 0 выполняется через `quality` на чистом checkout. Это максимально высокий seam: он проверяет, что lock-файл, код, тесты, security tooling и container baseline интегрированы как единая система. Отдельные tool-level тесты нужны только там, где агрегированная проверка не дает диагностической точности.

11. **Pre-commit.** Локальные hooks дают быструю проверку форматирования, lint и секретов, но не являются единственным контролем. Все обязательные проверки повторяются в CI, потому что hooks можно отключить.

12. **SAST.** Semgrep запускается с зафиксированными rulesets и fail-closed поведением. Ошибка запуска сканера считается провалом, а не успешным отсутствием находок. Изменение правил требует review SecOps/CODEOWNERS.

13. **Secret scanning.** Выбирается один основной CLI-сканер секретов, пригодный для локального и CI-запуска; baseline не должен скрывать новые находки без review. Рекомендуемый выбор для каркаса — Gitleaks. Реальные токены не используются в тестах; тестовые значения должны быть явно фиктивными.

14. **SCA и container scanning.** Trivy проверяет файловую систему/lock-файл и собранный smoke-образ. Gate блокирует `CRITICAL` и `HIGH` уязвимости, если для них доступно исправление. Неисправимые находки документируются временной Security Exception, а не бессрочным ignore без владельца и срока.

15. **SBOM.** Для smoke-образа создается CycloneDX или SPDX SBOM, связанный с commit SHA. SBOM сохраняется как CI-артефакт; публикация и подпись релизных образов будут определены отдельной фазой.

16. **Container baseline.** Минимальный smoke-образ использует multi-stage build, фиксируемый базовый образ, непривилегированного пользователя, read-only-friendly файловую модель и healthcheck там, где существует процесс сервиса. Запрещены `privileged`, host network, Docker socket и необоснованные capabilities. Секреты не передаются через build args и не включаются в слои.

17. **Compose baseline.** Начальная Compose-конфигурация должна валидироваться и демонстрировать именованные сети, но не обязана поднимать реальные `prod_net`/`honeynet` сервисы. Будущая сетевая топология принимается отдельно, чтобы не домыслить подсети, порты и ingress/egress из открытых решений `CONTEXT.md`.

18. **GitHub Actions.** CI запускается для pull request и основной ветки. Workflow имеет `contents: read` по умолчанию, явные минимальные permissions на уровне job, concurrency cancellation и timeout. Сторонние actions закрепляются на полных commit SHA. PR jobs не используют environment secrets и не запускают код в привилегированном окружении.

19. **Разделение CI jobs.** Быстрые проверки форматирования/lint/type/test и security scans выполняются независимо для понятной диагностики, но все являются required checks. Сборка smoke-образа начинается только после дешевых статических проверок. Ошибка любого required job блокирует merge.

20. **Отчеты CI.** Тестовые результаты, coverage, Semgrep/Trivy reports и SBOM связываются с commit SHA и сохраняются с ограниченным retention. Отчеты не должны содержать секреты, необработанную телеметрию или персональные данные.

21. **Branch governance.** Основная ветка защищается от прямых push и force push. Merge требует актуальной ветки, успешных required checks и как минимум одного независимого review. Изменения security controls, CI, dependency manifests и container baseline требуют review назначенного владельца.

22. **CODEOWNERS и SoD.** Владение отражает роли `Developer`, `DevOps` и `SecOps`. Один человек не должен единолично изменить прикладной код и ослабить проверяющий его security gate. Роль Auditor остается read-only и не входит в обязательных авторов изменений.

23. **Security Exception.** Исключение содержит идентификатор находки/правила, обоснование, область действия, владельца SecOps, компенсирующий контроль, дату истечения и ссылку на follow-up. Истекшее исключение автоматически перестает разрешать gate либо вызывает явный CI failure.

24. **Dependency updates.** Автоматизированный bot создает небольшие отдельные pull request для обновлений Python, GitHub Actions и container bases. Автомерж по умолчанию отключен; обновления проходят полный `quality` и review согласно CODEOWNERS.

25. **Документация.** Репозиторий описывает назначение AI-Sentinel без заявления о реализованных функциях, bootstrap, команды качества, структуру областей, процесс pull request, threat reporting, Security Exception и Definition of Done. `CONTEXT.md` остается нормативным словарем; архитектурные решения оформляются ADR.

26. **Commit policy.** Используются Conventional Commits и семантическое версионирование будущих артефактов. Проверка commit message обязательна для pull request либо при формировании merge commit; выбор squash/rebase фиксируется в настройках репозитория.

27. **Минимальный исполняемый артефакт.** Добавляется нейтральный smoke-пакет/команда, которая возвращает имя проекта и версию либо состояние `ok`, без сетевого API и бизнес-логики. Он доказывает package discovery, test discovery и container build. Он не называется AI Agent Core и не создает ложного впечатления реализованной подсистемы.

28. **Definition of Done Фазы 0.** Чистый checkout проходит bootstrap и `quality`; CI воспроизводит тот же результат; required checks могут быть подключены к Branch Protection; контейнер работает не от root; SAST/SCA/secret scans реально выполняются и fail closed; SBOM формируется; документация достаточна для нового Developer; в репозитории нет секретов и бизнес-логики следующих фаз.

## Testing Decisions

1. Тесты проверяют наблюдаемое поведение и репозиторные контракты, а не внутреннюю реализацию task runner, расположение временных файлов или порядок вызовов библиотек.
2. Главный acceptance test — запуск `quality` на чистом checkout после frozen bootstrap. Успех означает, что все обязательные локальные gates доступны через один стабильный интерфейс.
3. Отдельный smoke test запускает минимальный Python-артефакт как установленный пакет, а не импортирует его из корня рабочей директории. Это проверяет корректность packaging и `src` layout.
4. Отдельный тест проверяет поддерживаемую минимальную версию Python в CI. Быстрые jobs не обязаны дублироваться на всей матрице, если compatibility job покрывает minimum baseline.
5. Негативная проверка форматирования должна завершаться ошибкой на заведомо неформатированном fixture либо проверяться через режим `--check`; CI не должен молча форматировать код.
6. Негативная проверка secret scanning использует синтетический токен, распознаваемый тестовым правилом и не являющийся рабочим секретом. Сканер должен завершиться ненулевым кодом.
7. Негативная проверка Semgrep использует минимальный небезопасный fixture, чтобы доказать, что scanner действительно исполняется и fail-closed gate не является пустой командой.
8. Негативная проверка container policy проверяет, что root/privileged/host-network шаблон отклоняется policy check. Положительная проверка подтверждает непривилегированный UID smoke-контейнера.
9. Compose проверяется статически через итоговую нормализованную конфигурацию. Фаза 0 не запускает Honeynet, Netfilter или привилегированные интеграционные тесты.
10. Trivy проверяется на реальном lock-файле и собранном smoke-образе. Политика severity и поведение при сбое базы уязвимостей должны быть явными; недоступность сканера не считается успехом.
11. SBOM-тест проверяет, что документ синтаксически валиден, связан с собираемым артефактом и содержит сам smoke-компонент.
12. Тест документации/репозиторных правил проверяет наличие нормативного контекста, contribution/security guidance и отсутствие незаполненных обязательных шаблонов.
13. Конфигурация GitHub Actions проходит статическую проверку синтаксиса и security policy: минимальные permissions, SHA pinning, timeouts и отсутствие секретов в PR job.
14. CI не считается полностью протестированным только по локальному запуску: после создания GitHub-репозитория требуется реальный pull request, где все jobs выполняются и могут быть назначены required checks.
15. В текущем проекте нет prior art для тестов или CI. Фаза 0 сама устанавливает эталон, которому следуют последующие сервисы.
16. Новая бизнес-логика будущих фаз разрабатывается по Red-Green-Refactor; smoke-код Фазы 0 также создается с первоначально падающим поведенческим тестом.

## Out of Scope

- Реализация AI Agent Core, API Gateway, Prompt Guard, LLM Client, Triage Engine и Fallback.
- Определение JSON-контракта События безопасности, verdict, Evidence или корреляционного идентификатора.
- Интеграция с внешней LLM или локальной Ollama.
- Развертывание Cowrie, Target App, Nginx, Fluent Bit, DefectDojo или PostgreSQL.
- Реализация SOAR, Firewall Enforcer, iptables/nftables и любых host-level capabilities.
- Создание реальных сетей `prod_net` и `honeynet`, выбор подсетей, портов, TLS/mTLS и service authentication.
- Kubernetes/K3s, Ansible и production/test deployment pipeline.
- DAST, Chaos/Red Team Runner и экспериментальный корпус Prompt Injection.
- Определение SLO, RPO/RTO, retention производственных логов и backup/restore процессов.
- Реализация RBAC внутри будущих приложений; в Фазе 0 задаются только repository governance и CODEOWNERS.
- Выпуск production-образов, registry publishing, signing/attestation и автоматический production deploy.
- Получение сертификатов соответствия ISO/IEC 27001, NIST CSF или OWASP; каркас только поддерживает связанные практики.
- Численные пороги качества AI, Accuracy, Precision, Recall, F1, Attack Success Rate, Latency и MTTR.

## Further Notes

- Источником терминов и ограничений является `CONTEXT.md`. При конфликте спецификации с ним требуется ADR и обновление контекста до реализации.
- Репозиторий на момент подготовки спецификации не инициализирован как Git-репозиторий и не содержит исходного кода, CI или ADR. Поэтому решения Фазы 0 являются greenfield baseline, а не миграцией существующего toolchain.
- Выбор `uv`, Ruff, mypy, pytest, Gitleaks, Semgrep и Trivy фиксируется этой спецификацией как предлагаемый toolchain Фазы 0. Он согласуется с Python 3.10+, GitHub Actions, Semgrep и Trivy из контекста; Gitleaks и остальные инструменты вводятся как явные решения каркаса.
- Проверочный seam, принятый без дополнительного интервью, — агрегированная команда `quality`. Она должна быть стабильной для Developer и CI, даже если внутренние инструменты со временем изменятся.
- Численный coverage threshold, конкретный набор Semgrep rulesets, политика severity для уязвимостей без исправления и срок хранения CI-артефактов должны быть зафиксированы при декомпозиции в tickets, но не могут ослаблять fail-closed требования этой спецификации.
- Для публикации этой спецификации в issue tracker с label `ready-for-agent` необходимо сначала настроить tracker и словарь labels через `/setup-matt-pocock-skills`; в текущем каталоге отсутствуют Git remote и сведения о владельце GitHub-репозитория.
