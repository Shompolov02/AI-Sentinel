## Время и разделение данных

- Для каждой исходной записи хранится неизменяемое время первого приёма телеметрией.
  Для существующего события это сохранённое `received_at`, а не `tasks.created`,
  время анализа, mtime файла или дата миграции. Для новых сырьевых диапазонов,
  карантина и вспомогательных копий первый приём фиксируется в журнале очистки;
  нормализатор использует тот же момент, если диапазон уже зарегистрирован.
- `text_expires_at = first_received_at + 14 * 86400`; граница включительна:
  при `now >= text_expires_at` текст не выдаётся и не используется в новом анализе.
  Копия наследует срок исходника; объект из нескольких источников — самый ранний.
- По дополнительному выбору владельца при реализации пункта 6 TTY, служебные
  журналы и вспомогательные stdin/redirection-копии истекают от первого приёма
  начала сессии. Свежие фрагменты долгой сессии могут удалиться раньше собственных
  14 дней. Основные JSON-записи и команды Core живут по сроку каждой записи.
  Одинаковый текст разных записей не объединяет их основные сроки.
- Метаданные задачи и связанные с ней вердикт, объяснение без цитат, история,
  наблюдения входа и доказательства удаления истекают через 30 * 86400 от первого
  приёма события. Самостоятельные записи входа оператора и истории тревог — от их
  собственного времени. Поздняя обработка не начинает срок задачи заново.
  Для исторических метаданных без `received_at` резервной границей служит
  сохранённый `tasks.created`, а не дата миграции; текст при неизвестном сроке
  удаляется сразу. Квитанции collector сохраняют собственный deadline до удаления
  payload, затем удаляются без повторного чтения исходника. Операционные курсоры
  файлов и контекст источников сохраняются для новых записей, не как история задач.
- В Core добавляется отдельная таблица краткоживущего текста в прежней базе.
  Постоянное событие содержит безопасные поля и ссылку на текст; HTTP собирает
  прежний `event.command.text` до срока и возвращает null после него. Intake
  по-прежнему требует непустую команду: сохранённое очищенное событие не является
  повторно валидируемым входным `Event`.
- Объяснения текущих Rules/Fallback не содержат цитат. Будущие дословные цитаты
  и запросы LLM должны использовать явные краткоживущие объекты, а не свободный
  текст внутри долговечного reason/audit. LLM-клиент и его запросы в #51 не создаются.

## Хранилища и механизм очистки

### SQLite

Для Core и collector применяется одинаковый профиль соединений:
`secure_delete=ON`, `journal_mode=TRUNCATE`, `synchronous=FULL`,
`temp_store=MEMORY`; фактически применённые значения проверяются кодом.
Не применяются `secure_delete=FAST`, `journal_mode=OFF` или отключение журналирования.
После подтверждённой транзакции rollback-журнал должен быть нулевой длины.
Существующий hot journal сначала восстанавливает SQLite: удалять его вручную нельзя.

Миграция выполняет разделение текста, очистку уже просроченных/неизвестных данных
и одноразовый VACUUM для прежних свободных страниц. Если старая база использует
WAL, сначала завершаются её старые соединения, выполняются recovery/checkpoint
и переход на выбранный режим; файлы WAL не удаляются вслепую. На время миграции
Core ещё не готов к обслуживанию, а collector сохраняет долговечную доставку.
Нехватка места или ошибка очистки не отмечаются успешной миграцией.

SQLite документирует очистку содержимого обычных таблиц через
[secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete).
[VACUUM](https://www.sqlite.org/lang_vacuum.html) перестраивает базу и очищает
следы прежнего удалённого содержимого. Настройка temp_store не отменяет все
[транзакционные временные файлы](https://www.sqlite.org/tempfiles.html);
поэтому проверяются база, rollback/WAL/SHM и временные каталоги, а не только SQL-выдача.
Новые FTS/virtual tables, резервные копии и дампы с текстом не вводятся.

### Сырые и дополнительные копии Cowrie

- Отдельный процесс `retention` работает владельцем Cowrie UID/GID 999,
  non-root, без сети, capabilities и Docker socket. Реестр collector и его
  SQLite journal/lock разделяются через группу 999; directory 2770, files 0660.
  Collector остаётся UID 10001; Core SQLite и секреты не разделяются.
  Ему доступны только Cowrie logs, относящиеся к тексту stdin/redirection артефакты
  Cowrie downloads и состояние collector/очистки. Нет доступа к core-data,
  паролю, TLS-ключам, токенам или модели. Core и collector не получают права
  записи в исходные журналы; reader продолжает читать их read-only.
- В collector SQLite добавляется журнал диапазонов: идентичность/поколение,
  смещение и длина, неизменяемый срок, вид копии, состояние операции и безопасное
  подтверждение удаления. Он не содержит raw text. Доступ collector, retention
  и reader согласуется общим межпроцессным lock; изменение данных и реестра
  проходит через один протокол prepared → fsync диапазона → confirmed.
- Истёкшие завершённые JSON/текстовые диапазоны перезаписываются на месте с
  сохранением длины и перевода строки. Такие диапазоны распознаются по журналу
  удаления и больше не нормализуются как новые события. Свежие строки и ещё
  недописанный хвост не сдвигаются и не перезаписываются.
- При очистке первой строки меняется её fingerprint, но не логическое поколение.
  Реестр принимает только изменение, зарегистрированное протоколом очистки;
  произвольная подмена, truncation и копия на другом inode сохраняют прежние
  правила обнаружения. Незавершённая prepared-операция восстанавливается до
  сканирования/выдачи, чтобы crash не создавал новые ID и ложную потерю источника.
- TTY разбирается по кадрам закреплённого формата Cowrie. Заголовки и длины
  сохраняются, истёкшие payload-диапазоны очищаются; неполный кадр ждёт завершения.
  Переименование TTY при закрытии сессии отслеживается по идентичности файла.
  Все кадры наследуют срок начала сессии, включая её поздний вывод. Новая команда
  его не продлевает. Сессия берётся из штатного имени TTY либо события об артефакте;
  связь сохраняется по inode при переименовании. Служебные строки используют
  штатный префикс сессии, без сравнения команд и угадывания по timestamp.
  Неатрибутированная копия получает самый ранний из возможных сроков; неизвестный
  исторический срок означает согласованное удаление, а не новый TTL.
- Служебный журнал сохраняется в Cowrie volume через штатный
  `cowrie.python.logfile.logger` вместо `stdoutLogger`. Содержимое команд
  не дублируется в Docker logging storage. Диагностика runbook читает файл;
  журналы Core/collector/retention содержат только безопасные коды и ссылки.
  Исторические Docker-журналы требуют явной проверки при обновлении. Первое
  развёртывание включает штатное пересоздание только Cowrie-контейнера проекта
  с новым logger; старый контейнер с прежним Docker-журналом не оставляется
  архивной копией. Это однократное обновление, а не остановка при фоновой очистке;
  оно может завершить существующие сессии и выполняется по runbook обновления.
  При внешнем logging driver его данные проверяются отдельно до утверждения
  миграции. Удалять файлы Docker из приложения или подключать socket нельзя.
- Архивы, дополнительные stdin/redirection артефакты и переименованные файлы
  включаются в инвентаризацию. Неизвестный срок не восстанавливается по mtime:
  применяется согласованное миграционное удаление текста. Смешанные свежие
  диапазоны нельзя удалить вместе с целым файлом/архивом по старейшей записи.

### Завершённые gzip-архивы

JSON, служебные журналы и TTY в `.gz` очищаются потоково, без временного
распакованного файла. Для основной JSON-записи используется исходный receipt
после точной проверки длины и SHA-256 диапазона; логические смещения сохраняются.
Для TTY/служебных копий действует согласованный срок сессии. Исторический текст
без подтверждённого происхождения удаляется без назначения нового срока.
Заголовки gzip не сохраняют имя, комментарий или исходное время файла.

Журнал операции сохраняется до создания временного gzip. Готовый очищенный
результат и каталог синхронизируются, затем фиксируется его контрольная сумма.
Старый inode затирается до атомарной замены. Восстановление завершает готовую
замену или затирает незавершённый временный результат и повторяет построение;
переименование архива не оставляет временную копию вне обхода журнала.
Reader поддерживает зарегистрированные gzip-источники и прежние raw_record_ref.
Повреждённый архив или неподтверждённая замена дают ошибку очистки.
Внешний архиватор публикует только законченный файл атомарным переименованием
и не изменяет закрытый архив при обслуживании. Детали и доказательства —
[дополнение gzip](../acceptance/retention-issue-51-gzip.md).

### Outbox и chunks

Outbox сохраняет нормализованный payload до подтверждения доставки или срока;
после 202 текст можно удалить раньше, сохранив безопасную квитанцию и fingerprint.
Fluent Bit продолжает получать нормализованные события по прежнему пути.
Для очистки chunks collector сериализует передачу с delivery и выполняет
управляемую смену поколения буфера: останавливает только свой дочерний Fluent Bit,
очищает старые chunks и наполняет новый буфер из ещё допустимого долговечного
outbox. Нормализация в outbox продолжается при наличии ёмкости по политике #52;
Cowrie и сессии не останавливаются.
Ожидающие свежие события не теряются, их повторы безопасны по event_id.

Новый буфер не принимает события с истёкшим сроком. Смена поколения имеет
долговечные стадии и восстанавливается после crash; старые файлы не объявляются
очищенными до фактической очистки. Недоставленное истёкшее событие получает
критический локальный сигнал `buffer_event_expired`, без задачи и веб-тревоги.
Размеры, пороги и остальная политика перегрузки остаются #52.

Уточнение #52: локальное уведомление об истечении фиксируется атомарно с
удалением payload и публикуется после commit; ожидающее уведомление переживает
перезапуск. При откате commit ложный сигнал о потере не публикуется.
Принудительная остановка дочернего Fluent Bit перед очисткой не позволяет
graceful shutdown удалить имена chunks до усечения их inode. Отказ физической
очистки сохраняет намерение и даёт `retention_cleanup_failed`. Контракт и
доказательства — [buffer v1](collector-buffer-v1.md) и
[пункт 7 #52](../acceptance/buffer-issue-52-step-7.md).

## Работа по сроку, API и ошибки

- Фоновые исполнители рассчитывают ближайший deadline; при старте и пробуждении
  сначала обрабатывают уже истёкшие записи. HTTP/reader/delivery/worker проверяют
  срок независимо от фонового цикла. Плановых остановок Cowrie нет.
- Нельзя обещать физическое удаление в остановленной VM или при недоступном диске.
  Просроченный текст закрыт для выдачи/нового анализа; неуспешная физическая очистка
  даёт критический `retention_cleanup_failed` и остаётся незавершённой до повтора.
  Восстановление сначала завершает просроченную очистку; успешный health не
  подменяет её доказательство. Количественный SLO фонового удаления не вводится.
- `source_status=deleted` и raw HTTP 410 выдаются после подтверждения удаления
  источника. Одно наступление срока или ошибка reader не является таким
  подтверждением: при незавершённой очистке raw недоступен с 503, без фрагмента.
  Подтверждение хранится до срока метаданных, в том числе после очистки реестра.
- После 14 дней карточка/API показывают прежний результат и объяснение без цитат,
  `command.text=null`, без excerpt/raw_url. После 30 дней задача даёт 404 и не
  находится поиском. Права SecOps/DevOps/Auditor и no-store сохраняются.
- Для повторов хранится fingerprint исходного канонического события без текста.
  Пока задача существует, одинаковый повтор возвращает прежний ID/результат,
  конфликтующий — 409. Уже просроченный впервые доставленный источник и точный
  повтор после удаления 30-дневной истории получают 410 без создания задачи,
  анализа, записи команды или нового срока. Вечная история event_id не вводится.
- Обработчик проверяет deadline перед чтением текста и фиксацией результата.
  Незавершённая команда без достаточных безопасных данных завершается failed
  с причиной `text_expired` и предупреждением; вход может завершиться по оставшимся
  полям Rules. Уже готовый вердикт не пересматривается. Поздняя запись worker
  не возвращает удалённый текст/цитаты и не создаёт результат удалённой задачи.
- Удаление 30-дневной истории согласовано со связанными таблицами и pending-
  эпизодами CriticalAlerts: память не восстанавливает удалённые строки. Текущая
  реально наблюдаемая критическая проблема остаётся видна как актуальное состояние
  без сохранения старого task_id и старой истории сверх срока.
- Команда обслуживания `python -m ai_sentinel_core.retention --role ROLE --once`
  запускается внутри соответствующего контейнера; ROLE — core, collector или raw.
  На хосте она не принимает произвольные пути удаления; clock передаётся через
  доверенную конфигурацию тестового стенда, а не HTTP. Exit 0 — все уже наступившие
  операции этой роли завершены, exit 1 — ошибка/неполная очистка. Команда
  идемпотентна и не очищает неизвестные проекты, Docker volumes или secrets.

## Миграция и границы доказательства

Известный received_at сохраняется. Для неизвестного срока владелец разрешил
удалить только текст при миграции; безопасные факты и событие миграции остаются
в пределах своих сроков. Миграция не делает копию полной базы/сырья. Карантин
не содержит дублированного raw payload и очищается по сроку источника.

Проверяются действующие файлы томов и служебные временные файлы, включая данные,
доступные процессам через открытые файлы; результат не объявляется гарантией
стирания внешних snapshots, пользовательских экспортов или физических блоков SSD.
Откат на код без retention не считается сохранением политики: обновлённые тома
и смешанные версии нельзя обслуживать старым кодом без отдельной процедуры.

## Согласованные точки проверки TDD

Владелец 2026-10-26 согласовал все три seams. Каждый следующий сценарий проходит
отдельный red → green; все тесты заранее одним пакетом не пишутся.

| Граница | Наблюдение | Сценарии |
| --- | --- | --- |
| Настоящий нормализатор → POST /internal/events → API/карточка | ID, состояния, результат, Evidence, аудит и поиск | До/на/после 14 дней; 30 дней; задержанная доставка; replay; конфликт; restart; вход Rules и команда без текста |
| Команда очистки → реальные файлы и локальные сигналы | Exit code, отсутствие синтетического маркера, сохранность свежего маркера | Обе SQLite, journal/WAL/SHM, temp, outbox/chunks, JSON, TTY, служебные журналы, stdin-копии; миграция; crash/recovery; locked DB/ENOSPC; активный writer |
| Реальный Cowrie → Fluent Bit → TLS → Core/reader | Команда и вход видны до срока, затем текст физически отсутствует | Активная сессия переживает очистку; смешанный возраст/rotation; после срока raw 410, при ошибке 503; Guard; рестарт; права/no-store; прежняя сетевая изоляция |

Первый tracer bullet: настоящее нормализованное событие с уникальной синтетической
командой видно через API/карточку на 14 дней минус 1 секунда; при точном deadline
выполняется команда очистки и проверяется сохранённый результат без текста и
отсутствие маркера во всех файлах временного Core-хранилища. Отдельная свежая
команда сохраняется. Следующий цикл расширяет тот же наблюдаемый контракт на
collector и источник; публичное поведение не проверяется SELECT-ами таблиц.

Часы управляемые и общие для всех участников тестового стенда; отдельно проверяются
расхождение occurred_at/received_at/приёма Core, незавершённая задача и начатый
до deadline анализ. Допустимы подмены системного времени, внешнего транспорта
и отказов файловой системы; внутренние классы, таблицы и Guard не подменяют
проверяемое поведение. Реальная ML-приёмка использует закреплённые локальные веса.

После реализации: относящиеся pytest, `make test`, `make quality SECURITY_PYTHON=3.11`,
