# Collector buffer v1: согласованные решения #52

Основание: [issue #52](https://github.com/Shompolov02/AI-Sentinel/issues/52),
родительский #44, ADR 0002/0003/0007/0008 и `core-retention-v1.md`.
Владелец согласовал параметры и границы TDD в чате задачи #52.
Статус: согласованные ограничения и удаление реализованы; сквозная приёмка
Cowrie/TLS завершена в [пункте 8](../acceptance/buffer-issue-52-step-8.md).
Полный quality/security gate и эксплуатационная проверка завершены в
[пункте 9](../acceptance/buffer-issue-52-step-9.md); публикация PR — пункт 10.

## Ёмкости и перегрузка

- Core сохраняет существующий предел 1000 незавершённых задач.
- Outbox collector: 64 MiB нормализованных payload (67 108 864 байта).
- Дисковые chunks Fluent Bit: отдельный лимит 64 MiB.
- При достижении 80% любого лимита подаётся предупреждение; чтение новых
  записей замедляется в 5 раз относительно обычного режима.
- Приём новых записей останавливается перед превышением 100% любого лимита.
  Остановка сопровождается явным сигналом, без тихого удаления событий.
- Возврат к обычному чтению — после снижения всех контролируемых показателей
  до 60% или ниже. Доставка и очистка продолжаются во время ограничения приёма.
- Cowrie продолжает писать исходный журнал; остановка чтения collector
  не означает остановку Cowrie или его сессий.

64 MiB outbox относятся к payload, а не ко всему файлу SQLite. Страницы базы,
журналы транзакций и служебные метаданные требуют дополнительного места.
В пункте 6 добавлен технический предохранитель: чтение останавливается, если
фактическое свободное место меньше `2 * max(размер SQLite, 8 MiB) + 2 MiB`.
Минимум 18 MiB оставляет запас под rollback journal и ограниченную подачу
Fluent Bit; рост SQLite увеличивает резерв. Проверка расходует место на
настоящей файловой системе отдельного контейнера и наблюдает остановку/возобновление.
Это не резервирование блоков: сторонний writer может занять место после проверки.
Лимиты payload/chunks не являются квотой всего тома.
Это параметры лабораторного стенда, а не доказанные SLO производительности.

## Реализация ограничения приёма (пункт 6)

- `COLLECTOR_OUTBOX_BYTES` и `COLLECTOR_CHUNK_BYTES` передаются через Compose;
  значения по умолчанию — согласованные 67 108 864 байта. Для малых тестовых
  стендов минимум payload — 1024 байта, chunks — 4 MiB. Если одна запись
  больше настроенного бюджета payload, оператор должен увеличить бюджет:
  такая запись не пропускается и не удаляется молча.
- Обычный период чтения — 2 секунды, замедленный — 10. При достижении 80%
  текущий проход завершается после зафиксированной записи. При отказе по
  ёмкости курсор остаётся перед непринятой записью; её первый receipt сохраняется.
  Состояние ограничения переживает перезапуск и снимается при 60% или ниже.
- Подтверждённый payload outbox очищается сразу после приёма Core. Безопасная
  квитанция остаётся по прежнему сроку; отдельный deadline сохраняет обязанность
  очистить остаточную копию chunks через 14 суток.
- Supervisor помнит переданные, но неподтверждённые ID в текущем процессе и
  не добавляет их в chunks повторно на каждом цикле. Подача ограничена пакетами
  до 65 537 байт, pipe неблокирующий. Для нового пакета оставляется 2 MiB
  запаса chunks; остановка может наступить раньше абсолютного лимита.
  Лимит Fluent Bit с вытеснением старых chunks не включается.
- Перед запуском дочернего Fluent Bit старые chunks очищаются и восстанавливаются
  из допустимого outbox. Это допускает безопасный повтор доставки, но не потерю
  неподтверждённого события. Не требуется ждать доставки старой партии, чтобы
  добавить свежие допустимые записи в пределах бюджета.
- `POST /internal/events` сообщает `X-Core-Queue-Depth`; отказ из-за заполнения
  сообщает 1000. Новый авторизованный `HEAD /internal/events` через тот же TLS
  возвращает глубину без создания задачи и без тела. Collector опрашивает его
  раз в 2 секунды, чтобы снять ограничение даже при пустом outbox. Сбой опроса
  сохраняет последнюю известную глубину; сбой доставки остаётся виден в журнале.
- Loopback `GET /health` collector дополняется безопасными счётчиками
  `outbox_bytes`, `chunk_bytes`, `core_queue_depth`, режимом `intake`,
  `scan_interval_seconds`, `disk_reserve_bytes`, `disk_low`. Нового host-порта нет.
  Здоровый процесс может находиться в штатном режиме остановленного приёма.
- Локальные переходы: warning `collector_backpressure`, critical
  `collector_intake_stopped`, info `collector_intake_resumed`. Повторные
  наблюдения одного режима не создают новые записи перехода; текст событий
  в диагностике не публикуется.

### Координация с raw-очистителем (#52, пункт 8)

Retention overlay передаёт очистителю тот же `COLLECTOR_OUTBOX_BYTES`.
Живой collector остаётся единственным нормализатором: raw-очиститель проверяет
lease `fluent-owner.lock` и не вызывает `Journal.scan`, пока lease занят.
Если collector остановлен, обслуживающая команда может заполнить реестр
в пределах того же бюджета. Владелец при запуске настраивает lease как 0660
с группой 999; приватность chunks и Core не расширяется.

Доставка/reset используют отдельную блокировку buffer, не удерживая общую
блокировку SQLite во время TLS. Снимок ёмкости/режима выполняется за одно
соединение/транзакцию, без многократного ожидания registry lock.

Очистка несжатых TTY/служебных файлов обрабатывает до 64 диапазонов за порцию
и освобождает реестр между порциями. Локальная позиция и размер снимка файла
сохраняются до конца прохода: уже пройденный префикс не перечитывается в каждой
порции, а дописанный хвост этого файла обслуживается следующим вызовом.
Сначала commit prepared-намерений порции, затем запись и fsync файла,
затем commit erased-состояний. Нового TTL нет; после прерывания проход начинается
по долговечным состояниям реестра. Команда `--once` завершает весь проход либо
возвращает ошибку; освобождение lock между порциями не означает ложный успех.

## Срок хранения

Сохраняется политика #51: недоставленная запись истекает через 14 суток
от первого приёма, без продления при повторе или перезапуске. Проверка
использует управляемые часы и настоящий дисковый буфер, без изменения часов
хоста. Нужны физическая очистка просроченного текста outbox/chunks,
сохранность свежих записей и критический локальный `buffer_event_expired`.
Для записи, не принятой Core, задача и отдельная веб-тревога не создаются.

Отдельно согласован сценарий потери ответа после сохранения задачи Core:
collector может ещё считать событие недоставленным, хотя задача уже существует.
Повтор должен вернуть прежнюю задачу без повторного анализа. Отсутствие
подтверждения collector само по себе не доказывает отсутствие задачи Core.

### Уточнения удаления недоставленного (#52, пункт 7)

Удаление payload, постановка очистки chunks и безопасное уведомление об
истечении фиксируются одной транзакцией collector SQLite. Уведомление содержит
только event_id; задача и запись тревоги Core для него не создаются. Локальный
CRITICAL публикуется после commit. При откате commit payload остаётся и
`buffer_event_expired` не публикуется; команда очистки сообщает ошибку.
Ожидающее уведомление переживает перезапуск. После записи в журнал оно удаляется;
сбой между записью и подтверждением может повторить тот же event_id. Это
предпочтительнее молчаливой потери сигнала; гарантии exactly-once для внешнего
Docker logging driver не даются. Подтверждение logger не доказывает очистку chunks.

При смене поколения supervisor принудительно завершает только дочерний Fluent Bit
и дожидается его завершения. Затем усечение, fsync и unlink очищают файлы chunks
до снятия долговечного намерения очистки. Graceful shutdown для этой операции
не используется: Fluent Bit может раньше удалить имя файла, оставив байты
доступными через открытый дескриптор. Fresh outbox восстанавливает допустимые
записи в новом процессе. Cowrie и его сессии не завершаются этой операцией.

Истёкшая доставка в локальный `/deliver` получает 503 до очистки, без обращения
в Core: Fluent Bit должен дождаться очистителя, а не самостоятельно удалить
смешанный chunk как неисправимый. Это не меняет 410 для истёкшего нового события
в API Core или для подтверждённо удалённого raw-источника.
Физическая ошибка даёт CRITICAL `retention_cleanup_failed`; намерение очистки
остаётся для повтора. Collector завершается с ошибкой; после восстановления
доступа запуск сначала заканчивает очистку и только затем возобновляет подачу.
Отсутствие просроченного текста проверяется также через ранее открытый inode.

Невозможно выполнить физическое удаление в выключенной VM или на недоступном
носителе. Ошибка не считается успешной очисткой; истёкшие данные не доставляются
в Core. Полный путь Cowrie/TLS и эксплуатационная приёмка проверяются отдельно.

## Согласованные границы TDD

1. HTTP Core → API/страница: заполнение очереди, отказ без подтверждения новой
   задачи, повторная доставка и восстановление приёма; потеря ответа после
   сохранения задачи не создаёт вторую задачу.
2. Запущенный collector с настоящим Fluent Bit → локальные журналы и файлы:
   замедление, остановка, возобновление, перезапуск и физическое удаление
   просроченных данных при сохранении свежих. Файлы проверяются как результат
   работы буфера/очистки; внутренние таблицы не служат главным доказательством.
3. Cowrie → Fluent Bit → TLS → Core: полный сценарий с малым тестовым буфером,
   управляемым временем и проверкой прежней сетевой изоляции Cowrie.

Каждый сценарий реализуется отдельным red → green циклом через согласованную
границу. Нельзя заменять проверяемые внутренние компоненты моками или писать
все тесты заранее одним пакетом. Runtime-проверки используют собственные
тестовые данные и тома; действующий стенд пользователя не является фикстурой.
